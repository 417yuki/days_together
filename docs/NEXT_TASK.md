# 次の実装タスク

この文書は、Codexへ長い依頼文を毎回貼らずに済むよう、次の一件だけを記載する。

作業開始前に `AGENTS.md`、`docs/INDEX.md`、`docs/PRODUCT_SPEC.md`、`docs/ROADMAP.md` を読むこと。

## 対象

Milestone 6：パートナーチャットへの手動相談

## 目的

開花済みの「知らない芽」について、ゲームが送信用プロンプトを作り、ユーザーが普段のパートナーチャットへ手動でコピーし、返答を手動でゲームへ貼り付け、検証内容を確認してから安全に反映できるようにする。

このMilestoneでは、手動相談の最初の往復を完成させる。

- ゲームからLLM APIへ接続しない
- APIキーを要求しない
- ユーザー操作なしに文章を外部送信しない
- 貼り付けた返答を確認なしで反映しない
- 不正なID、不正JSON、古い依頼を反映しない
- 取込直前に端末内チェックポイントを作る
- 相談中も二人の位置、イベント、コーディの自律生活を止めない

## 今回の相談対象

対象イベントは `unknown_sprout` 一件だけとする。

相談を開始できる条件：

- `unknownSprout.status === "completed"`
- `unknownSprout.stage === "flower"`
- `path` が `"tended"` または `"watched"`
- まだ相談結果が反映されていない

返答から反映できる内容は次の三項目だけとする。

- `flowerName`：花の任意の名前。名前を付けない場合は `null`
- `partnerLine`：パートナー本人の短い一言
- `note`：花についての短い説明

イベントの `status`、`stage`、`path`、`choiceHistory` は変更しない。

## 基本ルール

- 手動相談はゲーム内の任意機能であり、相談しなくても花は完成状態のまま残る。
- 一つの花へ反映できる相談結果は、このMilestoneでは一件だけとする。
- 相談結果を反映済みの場合、新しい相談で上書きするUIは追加しない。
- 開発者パネルの「知らない芽を初期状態へ戻す」では、相談結果と保留中相談も初期化してよい。
- 相談プロンプトへ、会話履歴、個人名、私的な記憶、端末情報を自動で含めない。
- 今回プロンプトへ含めるのは、公開ゲーム名、イベントID、現在の花の経路、プリセット説明、返答形式、制約だけとする。
- 外部ネットワーク通信、Webhook、共有API、URL送信を追加しない。
- 動的文字列は `textContent` またはフォームの `value` で扱い、返答を `innerHTML` へ渡さない。
- JSON解析に `eval`、`Function`、動的importを使用しない。

## 1. データ型

少なくとも次の概念を分離する。

```ts
type ConsultationRequestType = "unknown_sprout_reflection";

type PendingConsultation = {
  requestId: string;
  requestType: ConsultationRequestType;
  eventId: "unknown_sprout";
  expectedStage: "flower";
  expectedPath: "tended" | "watched";
  prompt: string;
  createdAt: string;
  status: "pending";
};

type UnknownSproutConsultationResult = {
  schemaVersion: 1;
  requestId: string;
  requestType: "unknown_sprout_reflection";
  eventId: "unknown_sprout";
  expectedStage: "flower";
  expectedPath: "tended" | "watched";
  flowerName: string | null;
  partnerLine: string;
  note: string;
};

type AppliedUnknownSproutExtension = {
  requestId: string;
  flowerName: string | null;
  partnerLine: string;
  note: string;
  appliedAt: string;
};
```

型名やファイル分割は既存構造へ合わせてよい。ただし、保留中依頼、検証済みプレビュー、反映済み内容を同じ状態として扱わない。

検証済みプレビューはUIの一時状態でよく、ページ再読込後に復元しなくてよい。

## 2. requestId

- 相談を新規作成するたびに一意な `requestId` を発行する。
- `crypto.randomUUID()` が利用できる場合は使用してよい。
- フォールバックが必要な場合は `crypto.getRandomValues()` を使い、`Math.random()`だけで識別子を作らない。
- 保留中依頼は一件だけとする。
- 保留中依頼を明示的に破棄して作り直した場合、古い `requestId` の返答は検証で拒否する。
- requestIdはゲーム内照合用であり、認証トークンや秘密情報として扱わない。

## 3. 送信用プロンプト

開花済みのイベント詳細へ「パートナーに相談する」ボタンを追加する。

押した時に、現在の花の経路をスナップショットとして固定し、保留中相談を作る。

プロンプトには最低限、次を含める。

- 『ふたり日和』のゲーム内イベントについての相談であること
- イベント名「知らない芽」
- `eventId: unknown_sprout`
- `requestId`
- 現在の `stage: flower`
- 現在の `path: tended | watched`
- 手入れした花は淡い黄色、見守った花は白という現在のプリセット結果
- 花に名前を付けるかは任意であること
- パートナー本人らしい短い一言を求めること
- 現実の過去、未登録の人物、重大な危険を創作しないこと
- 新しいアイテム、場所、人物、次回イベントを作らないこと
- 下記のJSON形式を一つだけ返すこと

返答形式の例：

```json
{
  "schemaVersion": 1,
  "requestId": "ゲームが指定した値をそのまま返す",
  "requestType": "unknown_sprout_reflection",
  "eventId": "unknown_sprout",
  "expectedStage": "flower",
  "expectedPath": "tended",
  "flowerName": "ひだまり",
  "partnerLine": "この花、ここに来たかったのかもしれないね。",
  "note": "手入れを受けて咲いた、淡い黄色の小さな花。"
}
```

名前を付けない場合：

```json
"flowerName": null
```

プロンプトでは、短い自然文をJSONの前に添えてもよいが、JSONオブジェクトは一個だけにするよう指示する。

プロンプト生成は純粋関数へ分離し、同じ依頼データから同じ本文を作れるようにする。

## 4. プロンプト表示とコピー

相談画面へ次を表示する。

- 見出し
- 手動で普段のパートナーチャットへ送る説明
- 読取り専用の送信用プロンプト
- 「プロンプトをコピー」ボタン
- 「花へ戻る」または「相談をやめる」操作
- 次の返答貼り付け領域

コピーはユーザーがボタンを押した時だけ行う。

`navigator.clipboard.writeText()` が成功した場合は、読み上げ可能な状態表示で成功を案内する。

失敗した場合：

- ゲームを停止しない
- 読取り専用テキスト領域を選択しやすい状態へする
- 「長押ししてコピーしてください」などのフォールバック案内を表示する
- コピーできたと装わない

## 5. 保留中相談の保存

保留中相談は、ユーザーがパートナーチャットへ移動して戻っても失われないようIndexedDBへ保存する。

保存する：

- requestId
- requestType
- eventId
- expectedStage
- expectedPath
- prompt
- createdAt
- status

保存しない：

- 貼り付け途中の生返答
- 未検証のJSON
- 確認画面だけの一時状態
- クリップボード内容

ページ再読込後、妥当な保留中相談があれば相談画面を再開できるようにする。

壊れた保留中相談があってもゲーム本体を起動し、相談だけを安全に初期状態へ戻す。

## 6. 返答貼り付け

返答入力は複数行テキストエリアとする。

- 入力文字サイズは16px以上
- ラベルを付ける
- 最大受付文字数は20,000文字
- 上限を超える返答は解析せずエラーにする
- 入力内容を自動で外部送信しない
- 貼り付けただけではイベント状態を変更しない

「内容を確認」ボタンを押した時だけ抽出と検証を行う。

## 7. JSON抽出

返答の前後に短い自然文があっても扱えるようにする。

抽出優先順位：

1. `json` 指定のMarkdownコードブロック
2. 通常のコードブロック内のJSONオブジェクト
3. 本文中の波括弧が対応したJSONオブジェクト

ルール：

- 文字列内の `{`、`}`、エスケープを考慮した抽出にする
- 正規表現一個だけで入れ子JSONを切り出さない
- `JSON.parse`可能なオブジェクト候補を列挙する
- 配列を最上位結果として受け付けない
- 条件へ一致する候補がゼロならエラー
- 条件へ一致する候補が複数なら曖昧としてエラー
- 最初に見つかった候補を無条件採用しない
- 解析失敗で例外終了させず、修正して再試行できる案内を出す

抽出処理はDOMから分離した純粋関数へする。

## 8. 厳密な検証

JSONオブジェクトは次のキーだけを持つ。

- `schemaVersion`
- `requestId`
- `requestType`
- `eventId`
- `expectedStage`
- `expectedPath`
- `flowerName`
- `partnerLine`
- `note`

不足キーと未知キーを拒否する。

固定値：

- `schemaVersion === 1`
- `requestType === "unknown_sprout_reflection"`
- `eventId === "unknown_sprout"`
- `expectedStage === "flower"`

照合値：

- `requestId` が現在の保留中依頼と完全一致する
- `expectedPath` が保留中依頼と現在の花の `path` の両方へ一致する
- 現在もイベントが `completed / flower` である
- 相談結果がまだ反映されていない

文字列：

- 前後の空白を除去してから検証する
- `flowerName` は `null` または1文字以上24文字以下
- `flowerName` に改行を含めない
- `partnerLine` は1文字以上160文字以下
- `note` は1文字以上280文字以下
- 文字列以外を暗黙変換しない
- 制御文字を安全に除去または拒否する

検証後も表示は `textContent` を使用する。

不一致時に、ゲーム側のIDや現在状態を書き換えて返答へ合わせない。

## 9. 取込確認

検証に成功したら、すぐ反映せず確認画面を表示する。

表示する：

- 花の名前。`null` の場合は「名前を付けない」
- パートナーの一言
- 花の説明
- 対象イベント
- 対象経路
- 「この内容はまだ反映されていません」という案内

操作：

- 「反映する」
- 「返答を修正する」
- 「相談をやめる」

確認画面を開く、戻る、閉じるだけでは、花、イベント、二人の位置、コーディの行動を変更しない。

## 10. チェックポイントと反映

「反映する」を押した時だけ、取込処理を開始する。

反映前チェックポイントには最低限、次を保存する。

```ts
type ConsultationCheckpoint = {
  checkpointId: string;
  requestId: string;
  eventId: "unknown_sprout";
  createdAt: string;
  eventBefore: UnknownSproutState;
  extensionBefore: AppliedUnknownSproutExtension | null;
};
```

このMilestoneでは、チェックポイントから復元する通常UIは実装しない。復旧用データとして安全に保存し、将来の復旧画面へ接続できる構造にする。

取込時に行うこと：

1. 現在状態をもう一度照合する
2. チェックポイントを作る
3. 検証済み結果を反映済み拡張として保存する
4. 保留中相談を `applied` にするか、安全に終了状態へ移す
5. 保存成功後に確認画面を閉じる

チェックポイント、反映済みイベント内容、相談状態は、同じIndexedDBトランザクションまたは失敗時に部分反映を残さない同等の直列化で保存する。

既存の自動保存キューと競合させない。

保存が失敗した場合：

- 反映済みとして扱わない
- 花の表示を変更しない
- 保留中相談を残す
- 再試行可能にする
- 非モーダルまたは確認画面内で読み上げ可能に案内する

永続化成功前にStoreだけを確定状態へ進め、自動保存へ任せる実装は避ける。

## 11. IndexedDB

DBバージョンを2から3へ更新する。

既存ストアを削除、再作成しない。

追加するストア：

```text
consultations
keyPath: ["saveSlotId", "requestId"]

checkpoints
keyPath: ["saveSlotId", "checkpointId"]
```

`events` ストアの `unknown_sprout` レコードへ、反映済み拡張を任意項目として保存できるようにする。

バージョン2の既存セーブについて：

- 二人の位置を維持する
- 表示マップを維持する
- コーディの直近行動を維持する
- 知らない芽の段階、経路、選択履歴を維持する
- 相談結果は未反映として補完する
- 保留中相談はなしとして開始する

不正な相談、チェックポイント、拡張データがあってもゲーム本体を起動する。

既存イベント状態が正しければ、相談データだけを部分復旧する。

## 12. 反映後の表示

開花済みイベント詳細へ、反映した内容を表示する。

- `flowerName` がある場合は名前を見出しまたは補助見出しへ表示
- `flowerName === null` の場合は既存の「庭の小さな花」表示を維持
- `partnerLine` は引用として表示
- `note` は短い説明として表示
- 反映済みであることを分かるようにする

最近の出来事には、名前がある場合は「花に『名前』という名前がつきました」、ない場合は「花についてパートナーの言葉が残りました」程度の短い案内を表示してよい。

花マーカーの位置、二人の位置、イベント経路は変えない。

## 13. 画面とアクセシビリティ

- iPhone縦画面を優先する
- 320px幅で横スクロールを出さない
- 主要タップ領域は44px以上
- テキストエリアは16px以上
- 各入力へ視覚ラベルを付ける
- コピー、抽出エラー、検証成功、保存失敗、反映成功を `aria-live` で案内する
- エラー時は入力内容を保持する
- 詳細、相談、確認を戻った時に、可能な範囲で元の操作へフォーカスを戻す
- `prefers-reduced-motion`を維持する
- 長いプロンプトと返答が画面を横へ押し出さないよう `overflow-wrap` と縦スクロールを使う

## 14. 自動テスト

最低限、次をテストする。

### プロンプト

- requestId、eventId、stage、pathを含む
- `tended` と `watched` の説明が混ざらない
- JSON形式と制約を含む
- 個人データや会話履歴を参照しない

### JSON抽出

- JSONコードブロックから抽出できる
- 前後に自然文があっても抽出できる
- 文字列内の波括弧を壊さない
- JSON候補なしを拒否する
- 複数の一致候補を拒否する
- 最上位配列を拒否する
- 20,000文字超を拒否する

### 検証

- 正しい結果を受理する
- requestId不一致を拒否する
- requestType、eventId不一致を拒否する
- stage、path不一致を拒否する
- 未知キー、不足キーを拒否する
- nullの花名を受理する
- 空文字、長すぎる文字列、型違いを拒否する
- 既に反映済みの場合を拒否する
- イベント状態が変わった古い依頼を拒否する

### 状態と保存

- 貼り付けただけでは状態が変わらない
- 確認画面を開いただけでは状態が変わらない
- 明示確認でだけ拡張が反映される
- 反映前チェックポイントが作られる
- 保存失敗時に部分反映が残らない
- 保留中相談が再読込後に戻る
- 反映済み内容が再読込後に戻る
- DBバージョン2から3への更新で既存状態を維持する
- 壊れた相談データだけを部分復旧する

既存の移動、自律行動、イベント、保存テストを維持する。
