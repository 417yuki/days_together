# 次の実装タスク

この文書は、Codexへ長い依頼文を毎回貼らずに済むよう、次の一件だけを記載する。

作業開始前に `AGENTS.md`、`docs/INDEX.md`、`docs/PRODUCT_SPEC.md`、`docs/ROADMAP.md` を読むこと。

## 対象

Milestone 3：セーブが残る

## 目的

ブラウザを閉じたりページを再読込したりしても、主人公とコーディの現在地、および表示していたマップが端末内に残るようにする。

MVPの最初の保存実装として、ネイティブIndexedDBとメインセーブ一件だけを扱う。バックアップ、複数セーブ、画像Blob、イベント、パートナー設定はまだ実装しない。

Milestone 2の検品で見つかった小さなアクセシビリティ補修二件も、このPRの冒頭で一緒に直す。

## 保存の基本ルール

- 保存先はブラウザ内のIndexedDBとする。
- 外部サービスへ送信しない。
- メインセーブIDは `main` とする。
- 保存対象は、現在の実装で復元に必要な安定状態だけとする。
- 移動タイマー、移動途中の経路、画面メッセージ、開発者パネルの開閉状態は保存しない。
- 移動途中でページを閉じた場合、最後に到着済みの地点から再開する。途中の移動は再開しない。
- 読込や保存に失敗しても、ゲームを起動不能にしない。

## 実装する

### 1. Milestone 2の小補修

#### 移動中の読み上げ

`aria-live`領域の移動案内に、少なくとも次を含める。

- キャラクター名
- 現在地
- 最終目的地

例：

```text
主人公は玄関にいて、庭へ移動中です。
```

移動完了時は、到着地点を案内する。

#### 動きを減らす設定

`prefers-reduced-motion: reduce`の場合、経路を即時反映する既存動作に加えて、キャラクターピンの到着アニメーションも無効にする。

### 2. IndexedDB基盤

ブラウザ標準のIndexedDBを使用する。

- Dexie、localForageなどのランタイム依存を追加しない。
- DB名、DBバージョン、ストア名、メインセーブIDは定数へまとめる。
- `onupgradeneeded`で必要なストアを作成する。
- `versionchange`を受けた接続は閉じる。
- open、transaction、requestの失敗をPromiseとして扱い、未処理例外を残さない。

初期値：

```ts
const DB_NAME = "futari-biyori";
const DB_VERSION = 1;
const MAIN_SAVE_SLOT_ID = "main";
```

名称の微調整は可能だが、意味を変えないこと。

### 3. 今回作成するストア

製品仕様にある将来ストアを一度に全部作らず、今回必要な四つだけを作成する。

#### `appMeta`

- keyPath: `key`
- DBまたは保存形式のメタ情報を保持する

例：

```ts
{
  key: "schema";
  schemaVersion: 1;
  updatedAt: string;
}
```

#### `saveSlots`

- keyPath: `saveSlotId`
- 今回は `main` 一件だけ

例：

```ts
{
  saveSlotId: "main";
  createdAt: string;
  updatedAt: string;
}
```

#### `worldStates`

- keyPath: `saveSlotId`
- 表示中マップを保存する

例：

```ts
{
  saveSlotId: "main";
  viewedMapId: MapId;
}
```

#### `characters`

- 複合keyPath: `["saveSlotId", "characterId"]`
- 主人公とコーディの現在地を保存する

例：

```ts
{
  saveSlotId: "main";
  characterId: CharacterId;
  name: string;
  marker: string;
  mapId: MapId;
  locationId: string;
}
```

### 4. 保存用スナップショット

`AppState`全体をそのままIndexedDBへ入れない。

保存対象を取り出す純粋関数を追加する。

保存する：

- `viewedMapId`
- 主人公とコーディの `characterId`
- `name`
- `marker`
- `mapId`
- `locationId`

保存しない：

- `movements`
- `message`
- `developerPanelOpen`
- 移動タイマー
- DOM参照
- 関数
- 一時的なフォーカス情報

`activeNavigation`は今回保存せず、起動時は `map` から開始してよい。

### 5. 起動時の読込

初回描画で初期状態を保存してしまい、既存セーブを上書きしないこと。

起動順：

1. IndexedDBを開く
2. `main` セーブを読む
3. 保存データを検証する
4. 有効な部分を初期状態へ適用する
5. Storeを復元状態で開始する
6. 画面を描画する
7. 以後の自動保存を開始する

初回起動で保存が存在しない場合：

1. 現在の `initialState` を使用する
2. `main` セーブを作成する
3. 通常どおり起動する

読込中は、空の壊れた画面を一瞬表示せず、短い読込表示を出してよい。

### 6. 保存データの検証と復旧

IndexedDBの内容を無条件に `AppState` として扱わない。

最低限、次を検証する。

- `viewedMapId`が既知のマップである
- `characterId`が既知の主人公またはコーディである
- `mapId`が既知のマップである
- `locationId`がそのマップに存在する
- 同じcharacterIdが重複していない

復旧ルール：

- 不正な `viewedMapId` は初期値へ戻す
- 不正または欠落したキャラクターは、そのキャラクターだけ初期位置へ戻す
- 未知の余分なキャラクターは無視する
- 一部が壊れていても、有効な他のデータは利用する
- 読込後の `movements` は必ず空にする
- 読込後の `developerPanelOpen` は `false` にする
- 読込後の `activeNavigation` は `map` にする

検証と初期値への統合は純粋関数として分離し、テストする。

### 7. 自動保存

次の安定状態が変わったとき、自動保存する。

- `viewedMapId`
- 主人公の現在地
- コーディの現在地
- 初期状態へのリセット

移動では、各地点へ到着して `mapId` と `locationId` が更新された時点を保存対象とする。

保存は、`worldStates`、`characters`、`saveSlots.updatedAt`を一つのreadwrite transactionで更新する。

連続する状態更新で古い保存が新しい保存を上書きしないよう、次のどちらかを採用する。

- 保存処理を直列化するPromiseキュー
- 単調増加するrevisionを使い、最新スナップショットだけを確定する仕組み

単純な同時 `put` の投げっぱなしにはしない。

保存対象の内容が前回と同じ場合は、不要な書込みを省いてよい。

### 8. 保存状態とエラー表示

次の状態をUIで識別できるようにする。

- 読込中
- 保存利用可能
- 保存失敗

通常の保存成功を毎回大きく表示する必要はない。

読込または保存に失敗した場合：

- ゲームはメモリ上の状態で続行できる
- 非モーダルで読み上げ可能な案内を表示する
- 例：`保存できませんでした。この画面を閉じると変更が失われる可能性があります。`
- ユーザー操作を塞がない
- IndexedDBの内部エラー全文を通常画面へ表示しない
- 開発者向けには `console.error` などで原因を確認できるようにしてよい

### 9. リセット

既存の「初期状態へ戻す」は、次を満たす。

- 進行中の移動タイマーを停止する
- Storeを初期状態へ戻す
- 初期状態をIndexedDBへ保存する
- ページ再読込後も初期状態のままである

IndexedDBそのものやDBスキーマを削除する操作は追加しない。

### 10. 保存層の分離

UIやStoreからIndexedDB APIを直接ばらまかない。

少なくとも、次の責務を分ける。

- IndexedDBを開き、レコードを読み書きするアダプター
- 永続化するスナップショット型
- 保存データを検証し `AppState` へ統合する純粋関数
- 起動時読込と自動保存を調整する層

テストではIndexedDBへ直接依存せずに済むよう、保存リポジトリのinterfaceまたは同等の境界を用意する。

### 11. テスト

最低限、次を自動テストする。

- AppStateから保存対象だけを取り出せる
- `movements`、`message`、開発者パネル状態が保存対象に入らない
- 有効な保存データで表示マップと二人の位置を復元できる
- 不正なマップIDを初期値へ戻す
- 不正な地点IDを該当キャラクターの初期位置へ戻す
- 一人分のデータが欠落しても、もう一人の有効データを利用できる
- 未知のキャラクターを無視する
- 読込後に移動状態が残らない
- 初回起動でメインセーブを作成する
- 表示マップ変更を保存する
- 移動の各到着地点を保存する
- 保存処理が直列化され、古い書込みが最新状態を上書きしない
- リセット後の初期状態を保存する
- 読込失敗または保存失敗でもゲーム状態を利用できる
- 移動中の読み上げ文に現在地と目的地が含まれる

VitestのNode環境でブラウザIndexedDBが存在しないことを前提に、純粋関数と保存リポジトリのfakeを中心にテストする。テストのためだけに大きなランタイム依存を追加しない。

## 完成条件

- 初回起動時に `main` セーブが作成される
- 主人公とコーディの現在地が再読込後も残る
- 表示中マップが再読込後も残る
- 家と庭の移動途中で閉じた場合、最後に到着済みの地点から安全に再開する
- 移動状態とタイマーは再読込後に残らない
- 表示マップ変更、地点到着、リセットが自動保存される
- 壊れた一部データがあっても起動できる
- IndexedDBが利用できなくてもメモリ上で遊べる
- 保存失敗を非モーダルかつ読み上げ可能に案内する

- 動きを減らす設定でピンの到着アニメーションが無効になる
- 既存の移動、代理表示、マップ切り替え、開発者パネルが維持される
- typecheck、test、buildが成功する
- GitHub ActionsのCIが成功する
