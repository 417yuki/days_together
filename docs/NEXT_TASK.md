# 次の実装タスク

この文書は、Codexへ長い依頼文を毎回貼らずに済むよう、次の一件だけを記載する。

作業開始前に `AGENTS.md`、`docs/INDEX.md`、`docs/PRODUCT_SPEC.md`、`docs/ITEM_VISUALS.md`、`docs/ROADMAP.md` を読むこと。

## 対象

Milestone 8B-2：カテゴリ共通画像と詳細の三段フォールバック

## 目的

個別画像を用意していないアイテムや、個別画像の読込に失敗したアイテムの詳細へ、アプリ同梱の軽量なカテゴリ共通イラストを表示する。

アイテム詳細の表示優先順位を次で完成させる。

1. 読込に成功した個別画像 `imageAssetId`
2. 解決できるカテゴリ共通画像 `genericVisualKey`
3. 拡大した汎用SVGアイコン `iconKey`

画像が一枚もない場合、個別画像が壊れている場合、画像を削除した場合も、空白の画像枠やブラウザの壊れた画像表示を出さない。

## このMilestoneで変えないもの

- アイテム一覧は従来どおり汎用SVGアイコンを使用する
- 一覧で個別画像Blobやカテゴリ共通画像を読み込まない
- `ItemVisual` の既存フィールド名を変更しない
- `imageAssetId` は個別画像専用のままにする
- `genericVisualKey` はカテゴリ共通画像の解決に使用する
- `mapDisplayMode` は引き続き `"icon"` とする
- IndexedDBバージョンは6のままとする
- `assets`、`assetBlobs` ストアの構造を変更しない
- カテゴリ共通画像をIndexedDBへ保存しない
- 個別画像の追加、変更、削除、非同期世代管理を維持する
- アイテムの名前、カテゴリ、説明、sourceを変更しない
- 既存のマップ、イベント、パートナー設定、自律生活を止めない
- 外部通信を追加しない

## 1. カテゴリ共通画像レジストリ

アプリへ同梱する、静的なローカルSVGイラストのレジストリを用意する。

正確なファイル分割は既存構造へ合わせてよいが、意味として次を分ける。

```ts
type GenericVisualId =
  | "food"
  | "drink"
  | "plant"
  | "book"
  | "tool_craft"
  | "photo_memory"
  | "gift"
  | "furniture"
  | "clothing"
  | "small_goods";
```

10種類を上限ではなく今回の固定セットとして扱う。

### 1.1 イラストの役割

カテゴリ共通画像は特定のアイテムそのものを断定しない。

- `food`：皿、包み、焼き菓子等を抽象化した食べ物の情景
- `drink`：カップ、湯気、飲み物の情景
- `plant`：鉢、葉、芽の情景
- `book`：本、紙、手紙の情景
- `tool_craft`：工具、工作台、材料の情景
- `photo_memory`：写真枠、記録、思い出の情景
- `gift`：包み、リボン、贈り物の情景
- `furniture`：棚、椅子、室内装飾の情景
- `clothing`：布、衣類、縫い目の情景
- `small_goods`：箱、玩具、小物の情景

ブランドロゴ、既存作品の意匠、特定商品の形状を使用しない。

### 1.2 SVG実装

- 実行時に外部SVG、外部画像、外部フォントを取得しない
- ローカルTypeScript、ローカルSVGファイル、または静的なDOM生成として同梱する
- SVGはviewBoxを持ち、詳細の表示領域へ収まる
- 320px幅で横スクロールを起こさない
- 固定pxだけへ依存せず、幅100%相当で縮小できる
- CSS変数または既存テーマ色を使用し、テーマを壊す固定背景色へ依存しない
- 色だけでカテゴリを区別せず、形状を変える
- ユーザー由来文字列をSVGの `innerHTML` へ連結しない
- 静的なSVG定義へユーザー入力を埋め込まない
- Object URL、Data URL、Blobをカテゴリ共通画像へ使用しない

## 2. 既存キーからのエイリアス

現在のアイテムは14カテゴリごとの `genericVisualKey` を持つ。保存済みデータを移行せず、描画時の固定エイリアスで10種類の共通画像へ解決する。

次を固定する。

| genericVisualKey | GenericVisualId |
|---|---|
| `food` | `food` |
| `drink` | `drink` |
| `plant` | `plant` |
| `book` | `book` |
| `tool` | `tool_craft` |
| `craft` | `tool_craft` |
| `photo` | `photo_memory` |
| `memory` | `photo_memory` |
| `gift` | `gift` |
| `furniture` | `furniture` |
| `clothing` | `clothing` |
| `toy` | `small_goods` |
| `storage` | `small_goods` |
| `misc` | `small_goods` |

純粋関数または同等にテスト可能な関数を用意する。

```ts
resolveGenericVisualKey(key: string | null): GenericVisualId | null
```

ルール：

- 表のキーだけを解決する
- `null` は `null`
- 空文字は `null`
- 未知の文字列は `null`
- 大文字小文字を勝手に補正しない
- 前後空白を勝手に除いて既知扱いしない
- 未知キーで例外を投げず、拡大アイコンへフォールバックできる

## 3. 詳細の表示優先順位

既存の `resolveItemVisual` または同等の判定を、三段フォールバックが明示される形へ拡張する。

意味として次を扱えるようにする。

```ts
type ResolvedItemDetailVisual =
  | { kind: "individual"; assetId: string; url: string }
  | { kind: "generic"; genericVisualId: GenericVisualId }
  | { kind: "icon"; iconKey: string };
```

正確な型名は既存構造へ合わせてよい。

### 3.1 個別画像がない場合

- `imageAssetId` が `null`
- `genericVisualKey` が解決できる

この場合、詳細の主ビジュアルへカテゴリ共通画像を表示する。

### 3.2 個別画像がある場合

個別画像の取得と検証に成功した場合は、カテゴリ共通画像より個別画像を優先する。

- assetId一致
- ownerId一致
- MIME type、byteSize、Blobの検証成功
- 現在のアイテムと非同期世代が一致

既存の条件を緩めない。

### 3.3 個別画像の読込中

個別画像Blobの取得中も、空白の大枠にしない。

- 背景または主ビジュアルとしてカテゴリ共通画像を表示する
- 共通画像を解決できない場合は拡大アイコンを表示する
- `画像を読み込んでいます。` の読み上げ状態を維持する
- 読込成功後だけ個別画像へ置き換える

### 3.4 個別画像の欠損、破損、owner不一致、読込失敗

既存の日本語エラー案内を維持しつつ、表示は次へ戻す。

1. カテゴリ共通画像
2. 解決できなければ拡大アイコン

- アイテム本体を削除しない
- `imageAssetId` を表示処理だけで別アイテムへ付け替えない
- 自動で別のカテゴリ共通画像を推測しない
- エラーのたびにBlob取得を無限再試行しない

### 3.5 個別画像の選択プレビューと保存中

新しいファイルのプレビューがある場合は、プレビューを最優先表示する。

- プレビュー
- 保存中の同じプレビュー
- 失敗時に保持されたプレビュー

この間も既存のファイル名、形式、容量、保存、選び直し、キャンセルを維持する。

### 3.6 個別画像の削除

削除成功後は次へ戻す。

1. カテゴリ共通画像
2. 解決できなければ拡大アイコン

アイテム本体、名前、カテゴリ、説明は維持する。

## 4. アイコンへの最終フォールバック

次の場合は拡大アイコンを表示する。

- `genericVisualKey` が `null`
- `genericVisualKey` が空文字または未知
- 対応するレジストリ定義が欠けている
- カテゴリ共通SVGの生成で安全に扱えない状態になった

既存の未知 `iconKey` を `category` へ戻すフォールバックを維持する。

結果として詳細画面は必ず、次のいずれかを表示する。

- 個別画像
- カテゴリ共通画像
- 拡大アイコン

空白だけの主ビジュアルを出さない。

## 5. UIとアクセシビリティ

- 詳細の既存 `item-hero` または同等の領域を使用する
- 共通画像は主ビジュアルとして十分見えるが、アイテム名や説明を圧迫しない高さにする
- 320px幅で横スクロールを発生させない
- SVGは縦横比を維持する
- アイテム名、カテゴリ、説明、sourceの表示順を不必要に変えない
- 個別画像の追加、変更、削除ボタンを維持する
- タップ領域44px以上を維持する
- 共通画像はアイテム名が直後に表示されるため、原則として装飾扱いの `aria-hidden="true"` でよい
- 共通画像だけに意味を依存せず、アイテム名とカテゴリをテキスト表示する
- 色だけでカテゴリを区別しない
- 読込、保存、削除、エラーの `aria-live` を維持する
- `prefers-reduced-motion` を損なう新しいアニメーションを追加しない

## 6. 性能とライフサイクル

- カテゴリ共通画像はアプリ同梱の静的定義から同期的に表示する
- IndexedDBを読まない
- Blobを作らない
- Object URLを作らない
- revoke対象を増やさない
- 一覧表示時にカテゴリ共通画像DOMを作らない
- 詳細を開いた時だけ必要な共通画像DOMを作る
- パートナーの移動や自律行動による再描画で、Blob取得を新たに開始しない既存挙動を維持する
- 同じ詳細の無関係な再描画で、個別画像Object URLを不要に作り直さない
- 共通画像レジストリは副作用なしで解決できるようにする

## 7. 保存と移行

- `GameItem` の保存型を変更しない
- `genericVisualKey` を新しい値へ書き換えない
- 既存14キーは描画時のエイリアスで扱う
- SaveSnapshotへ共通画像DOM、SVG文字列、Blob、Object URLを入れない
- 既存セーブの移行処理を追加しない
- 個別画像を持つ既存アイテムを維持する

## 8. セキュリティとプライバシー

- 外部通信を追加しない
- 外部画像URLを追加しない
- ユーザー画像をカテゴリ共通画像として流用しない

- `innerHTML`、`eval`、`Function`、動的importを使用しない

## 10. テスト

少なくとも次を自動テストする。

### 10.1 レジストリ

- 10個の `GenericVisualId` が重複なく存在する
- 各IDから静的な共通画像定義を取得できる
- 未知IDを安全に扱う
- 外部URLを定義へ含めない

### 10.2 エイリアス

- 14個の既定 `genericVisualKey` が表どおり解決される
- `tool` と `craft` が `tool_craft` へ解決される
- `photo` と `memory` が `photo_memory` へ解決される
- `toy`、`storage`、`misc` が `small_goods` へ解決される
- `null`、空文字、未知キーが `null` になる

### 10.3 優先順位

- 有効な個別画像がカテゴリ共通画像より優先される
- 個別画像なしではカテゴリ共通画像になる
- 個別画像読込中はカテゴリ共通画像またはアイコンを表示できる
- 個別画像の欠損、破損、owner不一致ではカテゴリ共通画像へ戻る
- 個別画像削除後はカテゴリ共通画像へ戻る
- プレビュー中と保存中は選択画像が最優先になる
- 未知 `genericVisualKey` は拡大アイコンへ戻る
- 未知 `iconKey` でも最終的に `category` アイコンを表示できる

### 10.4 既存機能

- 一覧は汎用アイコンのままで、個別画像Blobを取得しない
- 個別画像の追加、変更、削除が維持される
- 非同期世代管理が維持される
- 登録フォームの一時ドラフト保持が維持される
- SaveSnapshotへ共通画像データを含めない
- DBバージョン6のままである

既存の移動、イベント、相談、パートナー設定、アイテム登録、個別画像、保存復元テストを維持する。

DOMテスト基盤を既に採用していない場合、無理に新しいブラウザテスト基盤を追加しない。純粋関数、静的レジストリ、既存UI構造を中心に確認する。
